## Section 0: Project Overview

### Product

**smartbidda** — a Bangla-first, gamified, AI-assisted Learning Management System for Bangladeshi primary-school students (Class 1-5) and their parents, following the NCTB syllabus.

### Description

smartbidda delivers the NCTB primary curriculum as voice-guided, quiz-gated lessons in child-friendly Bangla. Every completed module triggers a mandatory quiz; passing unlocks the next lesson, and failing summons an AI-curated remedial "Retake Class" that must be completed before a re-exam is available. Parents enter a separate Proxy Mode to watch progress in real time, cap screen time, and receive Bangla alerts when a weakness is detected. Its core value proposition is closing the loop without a teacher in the middle: detect the gap, assign the remedy, prove the recovery, tell the parent.

### Business Context

| Item | Detail |
|------|--------|
| **Business Model** | Freemium. Core NCTB lessons are free. A **per-family** monthly/annual subscription (all subjects, every linked child) plus separately-priced exam-time **crash-course packs** are paid through Bangladeshi MFS — bKash, Nagad, Upay — via SSLCommerz. `[📌 Adopted]` |
| **Core Value Proposition** | The only Bangla-first primary LMS that closes the loop automatically: weak topic detected → mandatory retake class assigned → re-exam unlocked → parent notified, with no teacher intervention. |
| **Competitive Differentiator** | Existing BD platforms ship a static video library. smartbidda gates progression on a mandatory quiz, auto-curates the remedial path from the student's own wrong answers, and gives the parent a Bangla proxy dashboard with screen-time control and a before/after recovery chart. |

### Goals & Success Metrics

| # | Goal | Success Metric | Measurement Method |
|---|------|---------------|-------------------|
| 1 | Students complete NCTB modules rather than abandoning them | ≥ 65% of started lessons reach a submitted quiz | `lesson_progress` joined to `quiz_attempt` — `completedAt IS NOT NULL / startedAt`, counted weekly |
| 2 | Students who fail recover, rather than stalling at the gate | ≥ 50% of failed quizzes result in a completed retake class and a passed re-exam within 7 days | `remedial_assignment` status = COMPLETED joined to `exam_attempt` re-exam score |
| 3 | Parents actually use the proxy dashboard | ≥ 30% of registered parents open `/parent` at least once per week | frontend event `parent_dashboard_view` + `parent_session` rows, counted weekly |
| 4 | Freemium converts to paid | ≥ 4% of families with 2+ active children convert to a paid plan within 90 days | `subscription` rows joined to `family` with `count(children) >= 2`, cohort query by signup month |
| 5 | The app is used, daily | ≥ 40% DAU/WAU among activated students (activated = completed ≥3 lessons) | `usage_heartbeat` distinct student per day ÷ distinct student per week |

> Every MVP feature below links to at least one of these goals; features are not orphans.

### Target Audience

Bangladeshi families with children in Class 1-5 (ages 6-11), where the parent (25-45) wants to monitor academic progress and screen time but cannot read the child's digital activity directly. Primary use is at home, on a shared or low-cost Android phone or a family laptop, on a mobile-data connection.

### User Relationships

A **Parent** has one to many **Students** (guardian link, max 3 by S5, admin-overridable). A **Student** belongs to exactly one acting Parent for proxy access. A **Teacher** authors content that is visible to every Student regardless of teacher. An **Admin** manages all Users of every type. A **Teacher** is a User row with `role = 2`, not a separate identity model.

## Section 1: Terminology

### Core Concepts

| Term | Definition |
|------|-----------|
| **Lesson** | The smallest learnable unit: one chapter's Bangla animated video plus its PDF material. Completing a Lesson is what triggers a quiz. |
| **Chapter** | An NCTB syllabus unit within a Subject for a given Class. Owns Lessons, topic tags, questions, and remedial content. |
| **Quiz** | The mandatory, auto-triggered assessment that fires immediately when a Lesson completes. Passing it is what unlocks the next Lesson. |
| **Quiz Session** | One student's live attempt at a chapter's quiz; holds the adaptive difficulty state and the in-flight answers. |
| **Term Exam** | A standardized exam per class — ১ম সাময়িক (First Term), অর্ধবার্ষিক (Half-Yearly), বার্ষিক (Annual). |
| **Pass Threshold** | The percentage below which a Quiz or Exam is a fail. Per-exam, default 60%. `[📌 Adopted: C3]` |
| **Weakness** | A topic tag on which the student answered below threshold across quizzes and exams. The unit the AI reasons about. |
| **Retake Class** | The mandatory remedial Lesson (video/PDF) auto-assigned for a detected Weakness. Must be completed before a Re-exam unlocks. |
| **Re-exam** | The second attempt at a failed Term Exam. Its availability is gated on all associated Retake Classes being COMPLETED. |
| **Parent Mode** | The proxy dashboard a parent enters after re-authenticating with their 6-digit PIN. |
| **Screen Time** | A server-side daily usage budget per child, enforced by heartbeat accounting, not by the client. |
| **Nudge** | A one-way on-screen prompt a parent sends to the child's device. Not a chat message. |
| **Family** | The billing unit: one parent account plus every linked child. One subscription covers a Family. `[📌 Adopted: C5]` |
| **Crash Pack** | A separately-priced, time-boxed bundle of exam-prep lessons sold at exam time. |
| **Leaderboard** | A per-class-number national ranking by points, restricted to display name + class. |

## Section 2: System Modules

### Module: Auth & Account

**Description:** Owns parent registration, child (student) profiles created by parents, and the two distinct login paths — a parent signing in with email+password, and a child entering via kid-PIN + avatar. Also owns the Parent Mode re-authentication gate.

**Main Features:**
- Parent signup with email + password, ToS + Privacy + Child Data Consent checkboxes
- Parent logs in → links up to 3 children (S5), each with class, avatar preset, and a 4-digit kid-PIN
- Student enters via `/auth/login` → picks child → enters 4-digit PIN (no password, no email) `[📌 Adopted: C1]`
- Parent Mode requires re-entry of a 6-digit parent PIN even while the parent session is live `[📌 Adopted: C2]`
- Account status enforcement (Suspended / Withdrawn), lockout after repeated failures

**Technical Flow:**

```
1. [Parent] opens /auth/signup and submits email + password + displayName + consents
2. Client validates inline (email RFC 5322, password min 8 + 1 number) → POST /api/auth/signup
3. Server validates uniqueness of email, hashes password (bcrypt), inserts user role=1 status=0
4. Server responds 201 { userId, status: "PENDING" } and sets the session cookie
5. Client routes to /onboarding → parent creates child: displayName, classNo, avatarPresetId, kidPinHash
   Client sends → POST /api/students
6. Server validates classNo ∈ [1..5], avatarPresetId ∈ [1..8], kidPin length = 4; inserts student
7. Server responds 201 { studentId, displayName } and sets user.status = 1 (ACTIVE)
8. [Student] opens /auth/login → selects the child → enters 4-digit PIN → POST /api/auth/student-login
9. Server verifies PIN against kidPinHash, checks user.status and screen-time budget
   → 200 { studentSession, remainingMinutes }  OR  401 { error: "PIN_INVALID" }
                        OR  403 { error: "SCREEN_TIME_EXHAUSTED" }
10. Client routes to / and renders the student shell
```

- **Success path:** signup → onboarding → child created → child enters with PIN → student shell renders.
- **Failure path:** wrong PIN 5× → `429 { error: "PIN_LOCKED" }` → client shows `ভুল পিন! আবার চেষ্টা করো।` then, at the limit, `অনেকবার ভুল হয়েছে। কিছুক্ষণ পরে চেষ্টা করো।` and disables the keypad.

**Real Scenario — Success:**

> **Actor:** Ritu (Parent, Dhaka)
> **Context:** Signing up for her son Arnab, Class 3
> **Action:** Creates an account with `ritu@example.com`, a password, accepts ToS/Privacy/Child-Data, then on `/onboarding` sets "Arnab", class 3, the fox avatar, PIN `1234`
> **Server Response:** `201 Created` — returns `{ studentId: "stu_7f2", displayName: "Arnab", classNo: 3 }`
> **UI Reaction:** Bangla success toast `অ্যাকাউন্ট তৈরি হয়েছে!` and Arnab's avatar card appears on the parent home.

**Real Scenario — Failure:**

> **Actor:** Arnab (Student, 8)
> **Context:** Entering the wrong PIN repeatedly after school
> **Action:** Taps `2222` four times, then `9999`
> **Server Response:** `429 Too Many Requests` — returns `{ error: "PIN_LOCKED", retryAfterSeconds: 300 }`
> **UI Reaction:** Keypad disables; `অনেকবার ভুল হয়েছে। ৫ মিনিট পরে চেষ্টা করো।` with a countdown, and the voice prompt reads the message aloud.

### Module: Localization & Voice

**Description:** Makes Bangla the default everywhere and keeps pre-literate children oriented through pre-authored Bangla voice-over assets. Owns the language toggle, the locale-aware string catalog, Bengali web fonts, and the voice-asset index.

**Main Features:**
- Bangla (default) ⇄ English toggle in Settings, persisted per user, applied on next render `[PM note: English subject content stays bilingual by design]`
- Every UI string, toast, validation message, empty state and confirm dialog authored in Bangla (Locale rule §3.2)
- Pre-authored Bangla VO assets keyed to navigation and state events, auto-played for students `[📌 Adopted: C8]`
- Bengali web fonts: Hind Siliguri (UI), Kalpurush (long-form PDF fallback)
- Voice respects the student's mute setting and `prefers-reduced-motion` / `prefers-reduced-data` hints

**Technical Flow:**

```
1. [Student] mounts any student route
2. Client reads user.locale (default "bn") → requests string catalog → GET /api/i18n/catalog?locale=bn
3. Server responds 200 { catalogVersion, strings: {...} }
4. Client renders with Bangla strings and the Hind Siliguri webfont
5. Client requests the VO index for the current route/state → GET /api/i18n/voice?locale=bn&event=lesson_mounted
6. Server responds 200 { audioUrl, durationMs } or 204 { silent: true } when no asset exists
7. Client plays the asset unless the student has muted voice
```

- **Success path:** student mounts the lesson route → Bangla catalog renders → the lesson's welcome VO plays.
- **Failure path:** VO asset missing for an event → `204` → the client renders silently **and logs a `voice_asset_missing` event** so the content gap is measurable rather than invisible.

**Real Scenario — Success:**

> **Actor:** Tamim (Student, Class 1, cannot read fluently)
> **Context:** Opens the app after school
> **Action:** Lands on `/`
> **Server Response:** `200 OK` — catalog `bn`, VO `{ audioUrl: ".../vo/home_welcome_bn.mp3", durationMs: 2100 }`
> **UI Reaction:** Bangla text renders and the voice says `আজকের ক্লাসে তোমাকে স্বাগতম!` while a large "শুরু করো" button pulses.

**Real Scenario — Failure:**

### Module: Quiz & Adaptive Assessment

**Description:** Fires a mandatory quiz the instant a lesson completes, adapts difficulty to the student's live accuracy, and is the sole gate on sequential progression.

```

5. Server records the answer, recomputes the tier from the last-10 window
   → 200 { nextQuestionId, tier, accuracy }
```

### Module: Term Exams & Remedial Loop

**Description:** The evaluation core. Three standardized exams per class, a per-exam pass threshold, AI weakness detection from the wrong answers, an auto-queued mandatory Retake Class, and a Re-exam gated on retake completion.

**Main Features:**
- ১ম সাময়িক (First Term), অর্ধবার্ষিক (Half-Yearly), বার্ষিক (Annual) per class
- Per-exam pass threshold, default 60% `[📌 Adopted: C3]`
- Below threshold → progression blocked, status `RETAKE_REQUIRED`
- Weakness detection maps wrong answers to topic tags → selects remedial content from the teacher-uploaded, topic-tagged library `[📌 Adopted: C4]`
- Mandatory Retake Class(es) auto-assigned; completion unlocks `RETAKE_COMPLETED` and the Re-exam
- 2 retakes per chapter, then escalation to the teacher `[📌 Adopted: S7]`
- Before vs. After progress chart on re-exam completion

**Technical Flow:**

```
1. [Student] opens /exams → GET /api/exams?classNo=3  → 200 [ { examId, titleBn, state, threshold } ]
2. Student starts an open exam → POST /api/exams/:id/attempts
3. Server verifies entitlement + screen-time remaining, creates exam_attempt status=IN_PROGRESS
   → 201 { attemptId, questionIds[], timeLimitMin }
4. Student submits answers → POST /api/exams/:id/attempts/:aid/submit { answers[] }
5. Server scores, compares to threshold
   PASS → attempt.status = PASSED, unlocks next module  → 200 { score, passed: true }
   FAIL → attempt.status = RETAKE_REQUIRED
6. Server runs weakness detection: aggregates wrong answers → topic tags weighted by error rate
   → selects remedial content per tag from the REMEDIAL library → POST (internal) remedial assignments
7. Server → 200 { score, passed: false, weakTopics[], remedialAssignmentIds[] }
8. Student completes each retake → POST /api/remedial/:id/complete
9. Server checks all assignments for this exam are COMPLETED
   → sets attempt.status = RETAKE_COMPLETED → 200 { reexamUnlocked: true }
10. Student takes the Re-exam → POST /api/exams/:id/attempts  { reexam: true }
    → server records the new score and computes the before/after delta
```

- **Success path:** exam passed → progression unlocked, parent notified of the score.
- **Failure path:** exam failed → next module locked, retake classes queued, parent receives the weakness alert, and the Re-exam button stays disabled until every retake is completed.

- **Failure path:** attestation unchecked → `422 { error: "RIGHTS_ATTESTATION_REQUIRED" }` → the publish button stays disabled with `অনুমতি নিশ্চিত করতে হবে।`

### Module: AI Analytics

**Description:** Two AI surfaces. The weakness detector (operational, inside the exam module) and the parent-facing predictive forecast. Both read the same per-topic answer history so they cannot disagree.

**Main Features:**
- Weakness detection: aggregates per-topic accuracy across quizzes + exams; a topic is weak below threshold over a minimum sample
- Remedial selection: maps weak topics to tagged REMEDIAL content, ordered by error weight `[📌 Adopted: C4]`
- Predictive forecast: estimates the likely term-exam band from recent daily quiz scores and names the chapters needing revision
- Every forecast carries its inputs so a parent can see *why*
- Rule-based topic scoring ships as the fallback path so an OpenAI outage degrades, not breaks, the loop

**Technical Flow:**

```
1. [Server] an exam attempt or quiz completes
2. Server aggregates the student's answers → per-topic accuracy over the window
3. Topics below threshold with sample >= 5 → weakness set
4. Server queries REMEDIAL content tagged with those topics, ordered by error weight
5. Server (fallback path, no AI) assigns directly; (primary path) sends the weakness set +
   candidate library to OpenAI with a strict schema, receives the selected content ids + rationale
6. Server validates the AI's selection against the library (unknown id → discard, fall back)
7. Server creates remedial_assignment rows and notifies the parent
8. On /parent/analytics the server recomputes the forecast from the same topic history
```

- **Success path:** wrong answers → weakness set → remedial selected → parent alerted with a named chapter.
- **Failure path:** OpenAI times out or returns an unknown content id → the server falls back to rule-based topic selection, logs `ai_selection_fallback`, and the assignment is still created — the loop never stalls on the model.

**Real Scenario — Success:**

> **Actor:** system
> **Context:** Nabila's science answers cluster on leaf structure and respiration
> **Action:** Detector runs after her first-term exam
> **Server Response:** internal → `200` — `{ weakTopics: ["উদ্ভিদের অংশ", "শ্বসন"], selected: ["lc_44", "lc_51"], confidence: 0.86 }`
> **UI Reaction:** Two Retake Classes appear for Nabila and the parent alert names `উদ্ভিদ` as the chapter.

**Real Scenario — Failure:**

> **Actor:** system
> **Context:** OpenAI returns a content id that is not in the library
> **Action:** Validation runs on the response
> **Server Response:** the unknown id is discarded, rule-based selection assigns `lc_44` instead, `ai_selection_fallback` logged
> **UI Reaction:** The student still receives a valid Retake Class; no user-visible error.

| DV-8 | Before/after recovery delta | `reexam_attempt.score − first_failed_attempt.score` | `GET /api/exams/:id/attempts/:aid` | `/exams/:examId/result`, `/parent/progress`, `/parent/alerts` |
| DV-9 | Weak-topic count | `count(DISTINCT topicTag WHERE accuracy < threshold AND sample >= 5)` | `GET /api/parent/dashboard` | `/parent`, `/parent/analytics`, `/admin/remedial`, `/quiz/:sessionId/result` |
| DV-10 | Lesson completion % | `count(lesson_progress WHERE watchedPct >= 95) / count(lesson_progress)` | `GET /api/curriculum/subjects` | `/learn`, `/`, `/parent/progress`, `/admin/students` |

> A row whose `Appears on` lists ≥2 screens and has no `Endpoint` would FAIL. Every row here has exactly one canonical endpoint; DV-1 in particular is the one that would otherwise be computed by the client on `/` and by the server on `/parent/screen-time` and disagree.

### 3.6 Identifier Display Rules (식별자 표기 규칙)

1. **A UUID is a primary key and nothing else.** It never appears on a screen, in a URL a user is expected to read, or in anything a support agent says aloud.
2. **An entity a person can QUOTE needs a readable reference.** The test is *"would someone say this on a support call?"*

| Entity | Internal key | Display column | Format |
|--------|--------------|----------------|--------|
| Family / parent account | `user.id` UUID | `family_code` | `SB-FAM-YYYYMMDD-NNNN` |
| Subscription | `subscription.id` UUID | `subscription_no` | `SB-SUB-YYYYMMNN-NNNN` |
| Payment | `payment.id` UUID | `payment_no` | `SB-PAY-YYYYMMDD-NNNN` |
| Term exam attempt | `exam_attempt.id` UUID | `attempt_no` | `SB-EXM-YYYYMMDD-NNNN` |
| Escalated remedial case | `remedial_assignment.id` UUID | `case_no` | `SB-CASE-YYYYMM-NNNN` |

**Not customer-quotable** (internal only, never displayed): `student.id`, `chapter.id`, `question.id`, `learningContent.id`, `notification.id`, `usage_heartbeat.id`. Students and chapters are identified by their Bangla title and class number, which is what a parent would actually say (`তৃতীয় শ্রেণির গণিত, ভগ্নাংশ অধ্যায়`).

> The student's 4-digit kid-PIN is a credential, not an identifier, and is never rendered or logged.
